## 3. Основная идея Nyamstack

Nyamstack — Telegram-бот для учёта КБЖУ.

Основные сценарии:
1. Пользователь вводит конкретный брендовый продукт.
2. Пользователь вводит обычное блюдо без точных данных.
3. Пользователь может вручную добавить свой продукт.
4. Продукты пользователей могут проходить модерацию и попадать в общую проверенную базу.
5. Все подтверждённые пользователем приёмы пищи сохраняются в дневной рацион.
6. Пользователь получает статистику по КБЖУ за день.

## 4. Разделение branded и generic

Это принципиальное архитектурное решение.

### `branded`

Пример:

`Простоквашино творог 5% 150 г`

Для такого ввода:
- ищем продукт в личной базе пользователя;
- затем в общей проверенной базе;
- используем известные КБЖУ продукта;
- пересчитываем их на фактический вес.

### `generic`

Пример:

`омлет из 3 яиц`

Такое блюдо не должно автоматически попадать в таблицу `products`.

Для него:
- LLM оценивает примерные КБЖУ;
- результат маркируется как оценка ИИ;
- после подтверждения пользователя приём пищи записывается в `meals`.

Это позволяет не смешивать проверенную продуктовую базу и приблизительные оценки LLM.

# 5. База данных

На текущем этапе зафиксированы четыре основные сущности:

- `users`;
- `products`;
- `user_products`;
- `meals`.

## 5.1. `users`

Назначение: хранить пользователя Nyamstack и его рассчитанную дневную норму.

### Поля

#### `id`
- тип: `INTEGER`;
- primary key;
- внутренний идентификатор пользователя Nyamstack.

Причина выбора `INTEGER`:
- идентификаторы являются целыми числами;
- диапазона `INTEGER` для проекта более чем достаточно.

#### `telegram_id`
- тип: `BIGINT`;
- `NOT NULL`;
- `UNIQUE`;
- не является primary key.

Назначение:
- найти пользователя по идентификатору Telegram.

Внутренние связи базы должны использовать `users.id`, а не `telegram_id`.

#### `created_at`
- дата и время создания пользователя;
- `NOT NULL`.

Назначение:
- анализ количества новых пользователей за период;
- базовые продуктовые метрики.

Точный вариант между `TIMESTAMP` и `TIMESTAMPTZ` пока не зафиксирован.

#### `calorie_target`
- тип: `INTEGER`;
- nullable.

#### `protein_target`
- тип: `INTEGER`;
- nullable.

#### `fat_target`
- тип: `INTEGER`;
- nullable.

#### `carbs_target`
- тип: `INTEGER`;
- nullable.

### Почему нормы nullable

Пользователь может уже существовать в базе, но ещё не рассчитать свою дневную норму.

### Что НЕ храним

На MVP не планируется постоянно хранить:
- цель (`lose / maintain / gain`);
- рост;
- вес;
- возраст;
- пол;

если они нужны только для единоразового расчёта нормы.

После расчёта сохраняется результат — дневная норма КБЖУ.

### Точность нормы

Дневные цели хранятся целыми числами:
- калории — целое число;
- белки — целые граммы;
- жиры — целые граммы;
- углеводы — целые граммы.

Для пользователя результат сравнения тоже отображается округлённо:

`не хватает 13 г белка`

вместо:

`не хватает 12.4 г белка`.

## 5.2. `products`

Назначение: общая проверенная база конкретных брендовых продуктов.

### Поля

#### `id`
- тип: `INTEGER`;
- primary key.

#### `name`
- тип: `TEXT`;
- `NOT NULL`;
- не `UNIQUE`.

Причина:

Продукты разных брендов могут иметь одинаковое название.

Например:
- `Простоквашино — Творог 5%`;
- `Село Зелёное — Творог 5%`.

Поэтому `name` само по себе не может быть уникальным.

#### `brand`
- тип: `TEXT`;
- `NOT NULL`;
- не `UNIQUE`.

В общей проверенной базе продукт обязан иметь бренд.

Обычные блюда без бренда относятся к `generic` и оцениваются LLM, а не сохраняются сюда.

#### `calories_per_100g`
- тип: `INTEGER`;
- `NOT NULL`.

#### `protein_per_100g`
- тип: `NUMERIC`;
- `NOT NULL`.

#### `fat_per_100g`
- тип: `NUMERIC`;
- `NOT NULL`.

#### `carbs_per_100g`
- тип: `NUMERIC`;
- `NOT NULL`.

### Точность КБЖУ продукта

План:
- калории на 100 г — целое число;
- Б/Ж/У — хранить с точностью до одного знака после запятой.

Например:

- 145 ккал;
- 12.4 г белка;
- 5.8 г жира;
- 3.1 г углеводов.

Конкретное ограничение точности `NUMERIC(...)` будет выбрано позже при написании реальной схемы.

### `usage_count`

Изначально предполагался `usage_count`, но на MVP он удалён.

Причины:
- это преждевременная оптимизация;
- количество использований можно вычислить по `meals`;
- отдельный счётчик создаёт дублирование данных.

Если позже `COUNT` по большой таблице станет дорогим, можно вернуться к денормализованному счётчику.

## 5.3. `user_products`

Назначение: личные продукты пользователя.

Пользователь может сразу использовать такой продукт в своём рационе, даже если продукт ещё не прошёл модерацию.

### Поля

#### `id`
- тип: `INTEGER`;
- primary key.

#### `user_id`
- тип: `INTEGER`;
- `NOT NULL`;
- не `UNIQUE`;
- foreign key → `users.id`.

Почему не `UNIQUE`:
- один пользователь может создать много продуктов.

### Что означает foreign key

Foreign key НЕ копирует значение из одной таблицы в другую.

Он означает, что ссылка должна указывать на существующую запись.

Например:

`user_products.user_id = 15`

разрешено только если существует:

`users.id = 15`.

#### `name`
- тип: `TEXT`;
- `NOT NULL`;
- не `UNIQUE`.

#### `brand`
- тип: `TEXT`;
- nullable;
- не `UNIQUE`;
- не foreign key.

Почему nullable:
- пользователь может добавить личный продукт без бренда;
- такой продукт всё равно может быть полезен в его личной статистике.

При этом отсутствие бренда может стать причиной, по которой продукт нельзя одобрить для общей таблицы `products`.

UX-идея:
- при ручном добавлении отдельно и явно спрашивать бренд;
- затем спрашивать название продукта;
- это уменьшит вероятность, что пользователь пропустит бренд просто потому, что не подумал о нём.

#### `calories_per_100g`
- тип: `INTEGER`;
- `NOT NULL`.

#### `protein_per_100g`
- тип: `NUMERIC`;
- `NOT NULL`.

#### `fat_per_100g`
- тип: `NUMERIC`;
- `NOT NULL`.

#### `carbs_per_100g`
- тип: `NUMERIC`;
- `NOT NULL`.

Продукт без КБЖУ в текущем MVP не имеет смысла, поэтому эти поля обязательны.

#### `moderation_status`

Булево значение (`true / false`) НЕ подходит.

Нужно минимум три состояния:
- `pending`;
- `approved`;
- `rejected`.

Причина:
- `false` не позволил бы отличить ожидающий модерации продукт от отклонённого.

Точный способ хранения пока не выбран:
- PostgreSQL `ENUM`;
- либо текстовое поле с ограничением.

Это будет решено позже.

#### `global_product_id`
- тип: `INTEGER`;
- nullable;
- не `UNIQUE`;
- foreign key → `products.id`.

До модерации:

`global_product_id = NULL`

После одобрения:

`global_product_id = id соответствующего products`.

Почему поле не `UNIQUE`:

Несколько пользователей могут независимо добавить один и тот же продукт.

Например:

- `user_products.id = 10 → global_product_id = 55`;
- `user_products.id = 27 → global_product_id = 55`;
- `user_products.id = 81 → global_product_id = 55`.

Все три записи могут соответствовать одному глобальному проверенному продукту.

После этого личный продукт пользователя можно считать связанным с проверенной записью.

#### `created_at`
- дата и время добавления;
- `NOT NULL`.

Оставлено для:
- сортировки очереди модерации;
- определения старых `pending`;
- аналитики количества пользовательских продуктов.

## 5.4. `meals`

Назначение: хранить факт добавления еды в рацион пользователя.

Одна строка `meals` означает:

> кто съел + что съел + сколько + итоговое КБЖУ этой порции + источник данных + время добавления.

### Поля

#### `meal_id`
- тип: `INTEGER`;
- primary key.

#### `user_id`
- тип: `INTEGER`;
- foreign key → `users.id`.

#### `name`
Название продукта или блюда на момент добавления в рацион.

Название сохраняется прямо в `meals`, чтобы история оставалась читаемой даже если исходный продукт позже:
- изменится;
- будет переименован;
- исчезнет из другой таблицы.

#### `weight_g`
Фактический вес порции в граммах.

Точный SQL-тип будет выбран позже.

#### `nutrition_source`

Показывает источник КБЖУ.

Допустимые значения:
- `approved_product`;
- `user_product`;
- `ai_estimated`.

Отображение для пользователя:

- `approved_product` → ✅ проверено;
- `user_product` → 👤 добавлено пользователем;
- `ai_estimated` → 🤖 оценка ИИ.

Название `nutrition_source` выбрано вместо `status_verification`, потому что поле описывает не процесс модерации, а происхождение данных.

#### `calories`
Итоговые калории конкретной порции.

#### `protein`
Итоговый белок конкретной порции.

#### `fat`
Итоговый жир конкретной порции.

#### `carbs`
Итоговые углеводы конкретной порции.

Для итоговых КБЖУ в `meals` планируется использовать точные дробные значения там, где они возникают.

#### `created_at`
Когда пользователь добавил еду в рацион.

# 6. Почему `meals` хранит готовый снимок КБЖУ

При добавлении продукта рассчитывается итоговое КБЖУ именно этой порции.

Например:

продукт:
- белки: 16 г / 100 г;

порция:
- 200 г;

в `meals` сохраняется:
- белки: 32 г.

После этого старый `meal` не должен пересчитываться из текущей версии `products`.

Причина:

Если позже данные продукта исправят с 16 до 17 г белка на 100 г, исторический рацион пользователя не должен внезапно измениться.

`meals` — это снимок события на момент добавления.

# 7. Правило округления

Принято общее правило:

> В базе и промежуточных вычислениях сохраняем достаточную точность. Округляем преимущественно при отображении пользователю.

Пример:

Если две порции содержат по 12.4 г белка:

точный расчёт:

`12.4 + 12.4 = 24.8 → показываем 25 г`

Если округлить каждую запись заранее:

`12 + 12 = 24`

появляется лишняя накопленная погрешность.

Поэтому:
- продуктовые БЖУ храним дробно;
- расчёты порций не округляем преждевременно;
- дневную статистику округляем для красивого отображения.

Дневные пользовательские цели при этом хранятся целыми числами.

# 8. Модерация

Базовый процесс:

1. Пользователь вручную создаёт продукт.
2. Запись появляется в `user_products`.
3. `moderation_status = pending`.
4. Пользователь уже может использовать этот продукт в своей статистике.
5. Модератор просматривает очередь.
6. Возможны два результата:
   - `approved`;
   - `rejected`.
7. При одобрении создаётся или определяется запись в `products`.
8. `user_products.global_product_id` начинает ссылаться на неё.

При этом разные пользовательские записи могут ссылаться на один глобальный продукт.

# 9. Текущие связи таблиц

Концептуально:

```text
users
  ├──< user_products
  └──< meals

products
  └──< user_products через global_product_id
```

То есть:

- `user_products.user_id` → `users.id`;
- `meals.user_id` → `users.id`;
- `user_products.global_product_id` → `products.id`.

# 11. Что пока НЕ зафиксировано окончательно

Эти вопросы нужно решить позже, когда начнётся реальная реализация схемы:

1. `TIMESTAMP` или `TIMESTAMPTZ` для дат.
2. Конкретные размеры `NUMERIC(precision, scale)`.
3. SQL-тип `weight_g`.
4. PostgreSQL `ENUM` или другой способ хранения:
   - `moderation_status`;
   - `nutrition_source`.
5. Поведение foreign key при удалении пользователя или продукта:
   - `CASCADE`;
   - `SET NULL`;
   - `RESTRICT`;
   - другие варианты.
6. Нужны ли дополнительные индексы.
7. Нужен ли составной `UNIQUE` для продуктов.
8. Как именно реализовать fuzzy search.
9. Как будет устроено удаление/редактирование пользовательских продуктов.
