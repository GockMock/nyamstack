# Гайд: Telegram-бот для подсчёта КБЖУ "Nyamstack"
Неофициальный гайд для себя — что делать, в каком порядке, где подводные камни.

---

## 1. Цель проекта

Не просто "ещё один бот-трекер", а проект, который показывает:
- полный бэкенд-стек (FastAPI, PostgreSQL, Redis, Docker, CI/CD)
- умение работать с внешними API (LLM)
- инженерное мышление в спорных местах (выбор источников данных, модерация, кэширование)
- реальных пользователей и метрики, а не просто код в репозитории

---

## 2. Общая логика бота

### 2.1. Поток обработки сообщения

```
Юзер пишет текст ("омлет из 2 яиц" / "Простоквашино творог 5% 150г")
        │
        ▼
LLM классифицирует и парсит текст в JSON:
  - generic (обычное блюдо, нет точных данных)
  - branded (юзер называет конкретный продукт/марку)
        │
        ├── generic ──► LLM оценивает среднее КБЖУ на 100г ──► помечается "🤖 оценка ИИ"
        │
        └── branded ──► поиск в user_products / products (нечёткий поиск по названию)
                │
                ├── нашли ──► берём точные цифры, помечаем "✅ проверено" или "👤 не проверено"
                │
                └── не нашли ──► просим юзера ввести КБЖУ вручную
                        │
                        ▼
                сохраняем в user_products (юзер сразу считает по этим данным)
                        │
                        ▼
                копия уходит в очередь на модерацию (status = pending)
```

### 2.2. Модерация (в фоне, не блокирует юзера)
- Ты отдельной командой (`/admin_review`) видишь список продуктов со статусом `pending`
- Одобряешь → продукт копируется в общую таблицу `products`, становится доступен всем с меткой "✅ проверено"
- Отклоняешь / дубль другого юзера → просто reject, не усложняем логикой дедупликации на входе
- Дубли на входе НЕ фильтруем (осознанное решение) — легче руками разгрести на модерации, чем городить сложный UI сравнения

### 2.3. Статистика
- `/stats` — агрегация по meals за день/неделю
- В идеале сразу видно, сколько данных "точных" (из products), сколько "оценка ИИ" — это же честность перед пользователем и хорошая деталь для собеседования ("мы прозрачно показываем погрешность данных")

## 3. Структура данных (кратко, без деталей типов — ты сам пропишешь)

- `users` — id, telegram_id, дневная норма (опционально)
- `user_products` — личные продукты юзера: id, user_id, name, brand, kbzhu (на 100г), moderation_status, global_product_id (nullable), created_at
- `products` — общая проверенная база: id, name, brand, kbzhu, usage_count
- `meals` — записи о приёме пищи: id, user_id, product_id (nullable) ИЛИ is_ai_estimated, weight_g, итоговые kbzhu, created_at

## 4. Этапы разработки (порядок действий)

1. **Определиться с LLM-провайдером и оплатой** (см. ниже раздел про оплату) — сделать это ДО написания кода, чтобы не переделывать промпты под другую модель
2. **Спроектировать БД** (ты делаешь сам)
3. **Настроить окружение**: Docker-compose (бот + Postgres + Redis), `.env` для секретов, ничего не коммитить в git
4. **Базовый флоу**: приём сообщения → LLM классификация → сохранение → ответ юзеру
5. **Ручное добавление продукта**: команда/кнопка "указать точные КБЖУ", запись в `user_products`
6. **Кэш и лимиты**: Redis кэш для одинаковых текстов (экономия на LLM), rate-limit на юзера (защита кошелька)
7. **Модерация**: `/admin_review` — простой интерфейс тебе, необязательно красивый
8. **Статистика**: `/stats`, можно текстом, можно графиком (matplotlib → картинка)
9. **Деплой**: VPS + Docker, CI/CD через GitHub Actions
10. **Набор пользователей**: 2-3 тематических чата/паблика
11. **Портфолио**: README с архитектурой, ссылка в резюме, по возможности цифры активности

## 5. Нюансы, о которых легко забыть

### 5.1. Технические
- **Rate-limit — must have с первого дня.** Без него один спамер сольёт весь баланс API за минуты. Ставь лимит и на количество сообщений, и (опционально) на дневной бюджет в токенах/рублях с автостопом.
- **LLM может галлюцинировать даже в JSON-формате.** Всегда валидируй структуру ответа кодом (pydantic-схема), а не доверяй "модель же обещала JSON".
- **Нечёткий поиск продуктов** — важно с самого начала, иначе "Простоквашино творог" и "творог Простоквашино" будут считаться разными записями. `pg_trgm` в Postgres или `rapidfuzz` на уровне приложения.
- **Кэш в Redis имеет смысл ключевать по нормализованному тексту** (нижний регистр, без лишних пробелов), иначе кэш почти не будет срабатывать.
- **Автопополнение баланса API** — включай с осторожностью или вообще не включай на старте: пока лимитов и мониторинга нет, лучше ручной контроль баланса, чем неожиданный счёт.

### 5.2. Продуктовые
- Юзеру всегда должно быть видно, откуда цифры: "🤖 оценка ИИ" / "👤 добавлено вами, не проверено" / "✅ проверено". Это не только честно, но и снижает количество обращений "почему цифры неточные".
- Продукты juzera, ожидающие модерации, у него всё равно должны нормально работать в его личной статистике — модерация не должна ощущаться пользователем как "барьер".

### 5.3. Организационные
- **Не жди идеального MVP** — выкатывай рабочую версию в 1-2 темы/чата, смотри на реальное поведение юзеров (какие блюда чаще всего пишут, какие продукты добавляют) и дорабатывай.
- Модерация продуктов — это твоя постоянная задача первое время, закладывай на это время каждую неделю, иначе очередь `pending` разрастётся, и юзеры не увидят пользы от "проверенных" продуктов.

## 6. Где нужна политика использования / согласие пользователя (коротко, неофициально)

Это не юридическая консультация, а просто список мест, где стоит явно предупредить пользователя внутри бота (например, командой `/privacy` или сообщением при первом старте):

1. **Сбор и хранение данных о питании** — юзер должен понимать, что бот сохраняет его сообщения о еде и вес продуктов в базу данных.
2. **Отправка текста в LLM API** — важно предупредить, что введённый текст (описание еды) уходит на сторонний сервер (OpenAI/OpenRouter/Yandex и т.п.) для обработки. Это первое, что может насторожить юзера, если он не в курсе.
3. **Продукты, добавленные пользователем, могут попасть в общую базу** — раз ты копируешь `user_products` в общую базу после модерации, стоит явно сказать: "название и КБЖУ продукта, который вы вводите, может быть добавлено в общую базу для всех пользователей (без привязки к вашему имени/аккаунту)". Это снимает вопрос "а почему мой продукт увидели другие".
4. **Хранение telegram_id** — обычная практика для ботов, но раз это персональные данные (хоть и обезличенные по сути) — короткое упоминание не помешает.
5. **Отсутствие ответственности за точность оценки ИИ** — короткая формулировка вида "данные, отмеченные как оценка ИИ, могут быть неточными, не используйте бота для медицинских целей" — простая защита и для юзера, и для тебя как автора.

Для pet-проекта этого достаточно в виде простого текстового сообщения по команде `/privacy` — полноценный юридический документ не нужен, пока это учебный/портфолио-проект без коммерческого использования персональных данных.

## 7. Что подсветить на собеседовании

- Осознанный выбор архитектуры хранения данных (свои + общая база + модерация) вместо "просто подключил чужой API"
- Разделение "оценка ИИ" / "точные данные" — думал о UX и доверии пользователя к данным
- Кэширование и rate-limit как защита от неконтролируемых расходов на LLM API
- Реальные пользователи и живая статистика использования, а не просто "работает на локалхосте"
